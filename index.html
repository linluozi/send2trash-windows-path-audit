Security audit · Windows path handling

send2trash was deleting the wrong file

Six reproduced defects in how the Windows backends turn a caller's string into a path — one of which destroyed a file the caller never named. Fixed, with a regression suite that fails on the unfixed code.

Upstream arsenetar/send2trash @ 522bafe · BSD 3-Clause · modified copy, see NOTICE.md

send2trash exists to delete files. Its callers are almost always responding to somebody pressing Delete, so path resolution is not an implementation detail — it is the safety property. A path that silently resolves somewhere else is worse than an error.

The package ships two independent Windows backends — SHFileOperationW through ctypes and IFileOperation through pywin32 — that each parsed paths on their own, with no shared normalisation step. Upstream had already fixed one defect of exactly this class (522bafe, a substring false-match in POSIX is_parent()), but that fix never touched Windows.

The clearest one

Hand send2trash a string that names no file — 'real.txt' followed by a NUL byte and some junk. The Shell item parser stops reading at the NUL, so the modern backend trashed real.txt and reported success: 

legacy   ArgumentError: argument 1: ValueError: embedded null character   -> file kept
modern   returned OK                                                      -> file deleted

Two backends, opposite behaviour, neither correct. This was the only defect in the audit observed destroying a real file, and it is why the rest of the list is worth reading.

Before and after

Findings

All six were reproduced against real files in a throwaway directory. None comes from a scanner. Severity is stated conservatively — only #4 was observed destroying a file; #2 and #3 were blocked by the operating system, not by the library, so they are filed as missing input validation rather than demonstrated exploits.

1

Absolute paths skipped normalisation

Functional

The absolute branch returned the caller's string untouched, so / separators, ./.. components, doubled separators and a trailing separator on a directory all reached the Win32 and Shell APIs verbatim. Neither API normalises paths, so every one of those forms was rejected and the file stayed on disk.

paths = [op.abspath(path) if not op.isabs(path) else path for path in paths]

in win/legacy.py:146, win/modern.py:24

Impact. Delete silently fails on legitimate input — anything built with pathlib or joined by hand.

2

An empty path resolved to the working directory

High

send2trash('') therefore asked the shell to recycle the process's own working directory, and '.' / '..' did the same for the CWD and its parent. The Freedesktop backend raises ENOENT for these inputs, so the two platforms disagreed — and Windows disagreed in the dangerous direction.

op.abspath('')  ==  os.getcwd()

in win/legacy.py, win/modern.py

Impact. On this machine Windows refused (WinError 161) because the CWD was in use, so no file was lost. The refusal came from the OS, not the library, so this is filed as missing validation rather than a demonstrated exploit.

3

\\?\UNC\ was sliced into a relative path

High

Dropping four characters from \\?\UNC\srv\share\f.txt leaves UNC\srv\share\f.txt — no leading separator, therefore relative. It resolves against the working directory, so a tree planted at ./UNC/srv/share/f.txt is what the operation would act on instead of the requested network path.

paths = [path[4:] if path.startswith('\\\\?\\') else path for path in paths]

in win/modern.py:26

Impact. A local decoy survived here only because the Shell item parser rejects relative paths outright. The protection is incidental; the library never guaranteed the path was correct.

4

An embedded NUL truncated the path — and deleted the wrong file

Critical

The Shell item parser stops at the NUL. The modern backend trashed real.txt and reported success, acting on a prefix of a string that names no file at all. The legacy backend raised ArgumentError for the same input, so the two backends behaved in opposite ways and neither was right.

send2trash('real.txt\x00anything')

in win/modern.py

Impact. The one defect in this audit observed destroying a real file. Reproduced, then fixed.

5

bytes paths decoded with the ANSI codepage

Medium

PEP 529 made the Windows filesystem encoding UTF-8; mbcs is the ANSI codepage. On this machine (cp936) a UTF-8 name round-tripped to mojibake, so the file was reported missing. ASCII names decode identically either way, which is why the first differential run showed no difference at all.

str(path, "mbcs")

in win/legacy.py:144, win/modern.py:22

Impact. Every non-ASCII filename passed as bytes fails on a non-UTF-8 ANSI codepage.

6

CoInitialize outside the try

Medium

CoInitialize is reference counted per thread and must be paired one-for-one with CoUninitialize. With the initialisation outside the try, any failure before the guarded block leaked a reference permanently. Measured: init=1 uninit=0 after a failed call.

pythoncom.CoInitialize()
fileop = pythoncom.CoCreateInstance(...)
                                   # ^ may raise: leaks the count
try:
    ...
finally:
    pythoncom.CoUninitialize()

in win/modern.py

Impact. A long-lived thread (notebook, GUI worker) can no longer tear its apartment down. The same failure escaped as pywintypes.com_error, which is not an OSError, so callers following the documented contract missed it.

The fix

Normalisation moved into one place that both backends call before touching any system API: 

paths = [normalize_win32_path(path) for path in paths]

normalize_win32_path(), in send2trash/util.py, now:

  • decodes bytes with os.fsdecode instead of mbcs;
  • rejects an embedded NUL with ValueError;
  • rejects '', '.' and '..' with ENOENT, matching Freedesktop behaviour;
  • always normalises, so separators and dot components are resolved;
  • keeps a trailing separator only for directories — stripping it unconditionally would turn 'file.txt/' into a request to delete file.txt;
  • translates the long-path prefix instead of slicing it, and keeps it for forms with no plain spelling such as Volume{GUID}.

modern.py additionally pairs CoInitialize with exactly one CoUninitialize and routes its whole COM body through _delete_items(), whose com_error conversion now also covers CoCreateInstance.

Scope. Three source files. plat_other.py, plat_gio.py, mac/*, win/__init__.py, win/IFileOperationProgressSink.py, __init__.py, __main__.py and exceptions.py are byte-for-byte identical to upstream, so POSIX and macOS behaviour is unchanged.

The first round scored 7/10, and two of the "kills" were false positives. Those mutants were syntactically invalid, so pytest exited non-zero with 0 failed and my exit-code check counted it as caught. Fixed by compiling every mutant before running, and by asserting on the failure count rather than the return code.

Three mutations also survived initially because the tests accepted "an OSError was raised" as success — the buggy code raised OSError too, for an unrelated reason. Those assertions were replaced with structural checks that spy on the final system call.

What is not covered

  • macOS and Linux were not exercised. Their code is byte-identical to upstream, so "no impact" rests on a diff, not a run.
  • plat_other.py keeps related weaknesses: an op.exists() pre-flight check and a counter-based collision loop that can race. Out of scope — no POSIX host was available to verify a fix.
  • The long-path prefix translation covers three forms only. Case-mixed input falls through to "keep the prefix", which fails loudly rather than deleting the wrong file: safe, but incomplete.
  • No fuzzing, no concurrency testing. Multi-path semantics were not audited.
